두 화면 모두 GitHub Pages에서 서버 실행 없이 열립니다. 기본 사용 경로는 HTML 버전입니다. 기존 다이어리 오른쪽 위의 ‘계획 · 실행 · 회고’ 링크로 이동할 수 있습니다.

이 폴더를 다이어리 프로젝트의 작업 기준으로 사용합니다. 사이트 호스팅과 배포는 별도 요청 시 진행합니다.

`index.html`을 브라우저에서 열면 사용할 수 있는 월간 다이어리입니다. 별도 설치나 빌드가 필요하지 않습니다.

- 종이 질감, 중앙 접힘 그림자, 겹친 종이 가장자리와 베이지색 배경
- 올리브 녹색 가죽 질감의 닫힌 다이어리가 첫 화면 중앙에 표시됩니다. 표지를 누르면 여섯 장의 속지가 차례로 펼쳐진 뒤 현재 월을 중앙에 보여줍니다.
- 표지는 처음 접속할 때 표시되며, 열고 난 뒤 표지로 돌아가는 버튼은 없습니다. 키보드 Enter/Space를 지원하며, 동작 줄이기 설정에서는 애니메이션 없이 바로 펼쳐집니다.
- 모든 달에 동일한 7열 × 6행 달력, 이전/다음 달 이동과 오늘로 이동
- 양쪽 아래 모서리를 0.22초 누른 뒤 안쪽으로 드래그하여 종이처럼 페이지 넘기기. 짧게 당기거나 Esc를 누르면 복귀하며, 키보드로 모서리에 초점을 두고 Enter/Space를 눌러도 넘길 수 있습니다.
- 날짜를 눌러 메모와 기분 작성, 수정, 삭제
- 월별 메모와 날짜별 기록을 브라우저 localStorage에 저장
- 좁은 화면에서는 다이어리 영역을 좌우로 스크롤

기록은 현재 브라우저에만 저장되며 다른 기기로 동기화되지 않습니다. 브라우저 데이터를 삭제하면 기록도 삭제됩니다. 안정적인 동일 주소 사용을 위해 로컬 서버에서 여는 것을 권장합니다. Google Fonts를 불러오지 못하면 기본 글꼴로 표시됩니다.

로컬 서버 예시: 이 폴더에서 `python -m http.server 5175` 실행 후 `http://localhost:5175`를 여세요.

## 과제6: HTML Plan–Do–See (기본)

- `pds/index.html` + `pds-model.js` + `pds-storage.js` + `pds-web.js`로 동작합니다. 입력·저장을 위해 브라우저 JavaScript가 필요합니다. Java와는 관계없습니다.
- 계획 기간·우선순위·성공 기준·예상 시간, 최초 계획과 수정 이력, 할 일 CRUD·검색·필터·정렬을 제공합니다.
- 실행 시작·종료·분 단위 실제 시간·막힘 사유를 할 일에 연결하고 중복 완료와 중복 실행 저장을 방지합니다.
- 집계 숫자를 눌러 근거 할 일로 이동하고 연결된 실행 기록을 볼 수 있습니다. 회고 개선점은 다음 계획에 연결됩니다.
- IndexedDB의 원자적 트랜잭션으로 같은 브라우저의 여러 탭에서도 중복 저장을 방지합니다. 새로고침 후 ID·값이 유지됩니다.
- 전체 PDS 기록을 JSON으로 내보내고 복원할 수 있습니다. 종이 다이어리의 기존 localStorage 메모는 건드리지 않습니다.
- 데이터는 해당 기기·브라우저·주소에만 저장됩니다. 다른 사람에게 자동 공유되거나 다른 기기와 동기화되지 않습니다. 브라우저 데이터를 삭제하면 잃을 수 있으므로 백업하세요.
- **이 HTML 버전은 서버 DB가 아닙니다. 과제의 서버 DB 영속화 조건(T06-C34)은 아직 충족하지 않습니다.** HTML 화면과 외부 DB를 연결하는 별도 작업이 필요합니다.
- 본인의 실제 기록은 직접 입력해야 하며, 예시 데이터를 제출용 실제 기록으로 만들어 넣지 않았습니다.
- 브라우저 저장 규칙: [contracts/pds-browser-v1.json](./contracts/pds-browser-v1.json)
- 검증: `node test-browser-model.cjs` · `node --check pds-web.js` · `node verify-turn.cjs`
- 표지 검증: `node --check cover.js` · `node test-cover.cjs`

## 과제 7 인증 구현 설명서 초안

공개 결과물 확인 주소: [여백 로그인](https://khn0916.github.io/diary/?login=1). 소스: [khn0916/diary](https://github.com/khn0916/diary). 과제 6의 마지막 가독성 반영본은 [202fc0c](https://github.com/khn0916/diary/commit/202fc0c35ce1d8d7066327424dd7423e766374d6)이며, 현재 이력에 포함되어 있습니다. 실제 제출에 사용한 고정 커밋은 제출 기록과 대조합니다.

### ① 무엇으로 붙였나

Supabase Auth와 `@supabase/supabase-js` 2.119.2를 사용합니다. 인증은 이메일과 비밀번호, 가입 확인 메일은 Brevo SMTP를 사용합니다. 비밀번호 해시는 Supabase Auth의 bcrypt가 맡습니다. 브라우저 코드는 공개용 키를 사용합니다. 이메일 가입은 공개 전까지 Supabase 설정에서 차단합니다.

### ② 왜 그걸 골랐나

기존 정적 화면과 페이지 넘김을 유지하면서, 비밀번호 해시와 인증 세션을 운영되는 서비스에 맡길 수 있어 선택했습니다. Python 서버에서 직접 인증하는 방법도 검토했지만 인증 서버와 세션을 별도로 운영해야 합니다.

### ③ 어디를 어떻게 고쳤나

- `diary-auth.js`는 `signUp`, `signInWithPassword`, `getUser`, `signOut`을 통해 가입·로그인·입장 확인·로그아웃을 처리합니다.
- `diary-cloud.js`가 다이어리와 계획 메모의 요청을 DB 함수로 보냅니다. [마이그레이션](./supabase/migrations/20261125000000_diary_accounts.sql)의 `require_session`은 토큰의 사용자·세션 ID가 활성 세션과 맞는지 검사합니다. 자료 API는 발급 후 24시간이 지났거나 로그아웃으로 세션이 삭제되었거나 비밀번호가 바뀌었으면 이전 세션을 거절합니다.
- 같은 파일의 `diary_documents`는 로그인한 계정으로 조회를 제한하고, 다른 소유자를 지정하면 404를 반환합니다. 자료 테이블은 비공개 스키마에 있고 브라우저에 직접 권한을 부여하지 않습니다.
- `diary-account.js`에서 브라우저 기록 이관, 전체 내보내기, 비밀번호 변경, 계정 삭제, 5일 사용 기록을 제공합니다.

### ④ 접근 차단 검증 기록

아래는 실제 마이그레이션을 적용한 **격리 PostgreSQL**에서 `node test-cloud-sql.cjs`로 검증한 SQL 결과입니다. `PT401`, `PT404`, `PT409`는 운영 PostgREST에서 각각 401, 404, 409로 매핑되는 사용자 정의 SQL 상태입니다. 공개 결과물의 HTTP 요청·응답 증거는 운영 적용 후 별도로 채웁니다.

| 요청 | 테스트 성공 결과 | 테스트 거절 결과 |
| --- | --- | --- |
| `diary_documents('get', 'journal')` | A의 유효 세션으로 A의 자료 조회 | 로그인 없는 세션 `PT401` |
| `diary_documents('get', 'journal', owner)` | A와 B 모두 본인 자료 조회 | A→B, B→A 모두 `PT404` |
| `diary_documents('put' / 'delete', 'journal', owner, version, …)` | 본인 자료 생성 및 버전 확인 | 양방향 타인 수정·삭제 `PT404`, 거절 전후 본인 자료 1건과 내용 동일 |
| `diary_documents('list', …)` | A와 B 목록에 각각 본인 자료 1건만 반환 | 타인 소유자 값을 요청에 넣으면 `PT404`, 원본 테이블 직접 조회 `42501` |
| 같은 `diary_documents('list')` 요청 | 유효 세션에서는 본인 자료 반환 | 세션 삭제 뒤 동일한 사용자·세션 주장으로 `PT401`, 비밀번호 변경 후도 `PT401` |

로컬 해시는 인증 시스템을 흉내 낸 값입니다. 실제 두 테스트 계정에 같은 비밀번호를 넣어 bcrypt 저장값이 달라지는 증거는 운영 계정 검증에서 따로 남깁니다. 요청 기록에는 비밀번호, JWT, SMTP 키 원문을 넣지 않습니다. 성공한 운영 초대 메일과 수신 확인은 SMTP 연결 검증이고, 가입·자료 접근 실측은 별도입니다.

### ⑤ AI와 나

- AI에게 맡긴 일 — 계정별 서버 저장, 세션 검사, 기존 UI 연결과 접근 제어 테스트.
- 내가 직접 판단한 일 — 종이 다이어리 흐름을 유지하고 공개 가입은 마지막에 연다.
- AI 제안을 따르지 않은 일 — 실제 5일 기록은 본인이 남긴다. 제출 시 자신의 경험에 맞게 확정한다.

### ⑥ 아직 못 막은 것

브라우저에서 실행되는 악성 확장이나 같은 출처의 스크립트는 세션이 살아 있는 동안 사용자 권한으로 요청할 수 있습니다. 현재 서버 저장은 계정 단위이며 같은 계정의 여러 기기 사이에 즉시 알림을 보내지 않습니다. 새로고침이나 화면 포커스 시 기록을 다시 읽습니다. 기존 브라우저 원본과 내려받은 파일은 서버에서 계정을 삭제해도 해당 기기에 남습니다.

### 과제 확인 및 실사용

1. [여백 로그인](https://khn0916.github.io/diary/?login=1)을 열고 본인 계정으로 들어갑니다.
2. 기록을 남긴 브라우저에서 계획 메모 하단 **계정과 전체 기록 → 이 브라우저의 기록 옮기기**를 열고, 종류별로 이관해 새로고침합니다.
3. **5일 사용 기록**은 1~5일차 목록으로 표시됩니다. 할 일의 **실행 노트**에 당일 실제 작업을 처음 저장하면 관찰 질문·실제 작업 시간(분)·처음 계획 규칙이 고정되고, 해당 실행의 계획이 5일 동안 연결됩니다. 같은 계획의 실행을 저장할 때 서울 기준 당일 작업 합계와 근거가 자동으로 반영됩니다. 같은 날짜의 추가 작업은 같은 줄에 합산됩니다. 2일차 기록 뒤 3일차 작업을 시작하기 전에 바꾼 규칙과 이유를 입력합니다.

통과 기준은 같은 계정에서 이관한 기록이 보이고, 5일 전체 및 변경 전후의 합계·평균을 손계산과 대조할 수 있는 것입니다. **5일 사용 기록 → 집계와 근거 기록 보기**를 열면 기존 실행·회고 화면에서 같은 5일 집계 및 일별 실행 근거를 확인할 수 있습니다. 로그아웃 상태나 만료된 세션의 자료 요청은 401이며, 화면은 다시 로그인을 요청합니다. 테스트용 기록은 실제 사용 기록으로 제출하지 않습니다.

## Vercel 배포

Vercel은 GitHub의 `main` 브랜치에서 `node build-vercel.cjs`를 실행하고 `dist/`의 웹 파일을 게시합니다. GitHub Pages와 Vercel은 같은 Supabase 프로젝트의 계정과 서버 기록을 사용합니다. 호스트마다 브라우저 저장소가 구분되므로 새 주소에서는 다시 로그인합니다. GitHub Pages 브라우저에만 남아 있는 이전 기록은 그 주소에서 계정으로 옮긴 후 Vercel에서 열 수 있습니다.

이메일 확인을 사용할 때는 Supabase Auth의 Redirect URLs에 Vercel 운영 주소와 기존 GitHub Pages 주소를 각각 정확히 등록합니다.

## 이전 Python·SQLite 구현 (보존)

Python·SQLite 서버 코드는 삭제하지 않고 별도로 보존합니다. `style.css`, `app.js`는 그대로이며, 기존 `index.html`에는 HTML 과제 화면으로 가는 탐색 링크와 링크용 CSS만 추가했습니다. 아래 Python 주소는 선택적으로 로컬 서버를 실행할 때 사용하는 주소입니다.

```text
python server.py
```

- 원래 다이어리: http://127.0.0.1:5175/
- 계획·실행·회고: http://127.0.0.1:5175/pds
- Python 3.10 이상, 표준 라이브러리만 사용하므로 패키지 설치가 필요하지 않습니다.
- PDS 기록은 `data/diary.sqlite3`에 저장됩니다. `PDS_DB` 환경 변수 또는 `--db` 옵션으로 저장 위치를 지정할 수 있습니다.
- 원래 다이어리의 메모는 기존대로 브라우저에 저장됩니다. PDS 데이터만 서버 DB에 저장되며 두 저장소를 자동으로 합치지 않습니다.
- 계획 이력, 할 일 CRUD·검색·필터·정렬, 실행 기록, 중복 완료 방지, 회고 집계와 근거 링크, 개선점의 다음 계획 연결, 전체 JSON 내보내기를 제공합니다.
- 최초 DB는 비어 있습니다. 본인의 실제 기록은 나중에 직접 입력합니다.
- 로그인과 접근 제어가 없습니다. **배포한 링크를 아는 사람은 조회뿐 아니라 생성·수정·삭제·전체 내보내기도 할 수 있습니다.** 공개해도 괜찮은 내용만 입력하세요.
- 기본 실행은 로컬 컴퓨터에서만 접속 가능합니다. 호스팅은 별도 요청 후 진행하며, Python 실행과 영속 DB 저장 공간이 필요합니다. GitHub Pages는 Python 서버를 실행하지 않습니다.
